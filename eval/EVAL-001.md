# EVAL-001：评审团机制验证实验（埋雷 PR 对照实验）

> 日期：2026-10-28 ｜ 目的：在写插件骨架之前，先验证"多 persona 评审团 + voter 复核"这个核心机制是否优于单审，以及如何量化评审质量。

## 1. 实验设计

- **语料**：`corpus/pr-001/pr-001.diff`（97 行统一 diff，TS checkout 模块新增折扣码功能），人工预埋 8 个 bug（`gt/pr-001.gt.json`，评审 agent 不可见）：
  - B1 浮点金额、B2 off-by-one（`>` vs `>=`）、B3 SQL 注入、B4 IDOR 越权、B5 支付前扣额度、B6 吞异常、B7 断言固化浮点、B8 it.skip 禁用测试
- **Baseline**：1 个通用高级评审员 agent，"全面审查，不预设方向"
- **评审团**：4 个 persona finder（正确性/安全/设计/测试完整性）并行、各自独立上下文 → 去重得 14 条 finding → 14 个独立 voter 逐条复核（valid/invalid/uncertain + 证据 + 置信度）
- **评分**：与 ground truth 语义匹配计召回；误报 = 不成立的 finding

## 2. 结果

| 指标 | Baseline 单审 | 四人评审团 |
|---|---|---|
| 召回（8 雷） | **5/8**（中 B1/B2/B3/B5/B8；漏 B4 IDOR、B6 吞异常、B7 断言固化） | **8/8** |
| 雷外有效发现 | 1 条（并发竞态） | 6 条（并发竞态、percentOff 未校验、日志泄密、txId 契约、mock 未验证金额、覆盖缺口） |
| 误报 | 0 | 0 |
| 单视角依赖 | — | **8 雷中 6 个仅 1 个 persona 发现**（B2/B3/B4/B6/B7/B8） |
| voter 复核 | — | 14/14 valid（置信度 0.98–0.99），零误杀 |
| 证据质量 | 全部带文件+行引用 | 全部带文件+行引用；voter 二次定位确认 |

## 3. 结论

1. **机制成立**：召回 5/8 → 8/8（+60%），且增量全部来自 persona 间的视角互补——6/8 的 bug 只有一个视角看到。实测复现了 Addy Osmani 的"93.4% 异质性"论断（本实验 75% 单视角命中）。
2. **voter 环节零误杀**，但本轮 finding 全是真发现，**过滤能力未被测试到**——需要带噪声的 finder 配置（如弱模型/宽松 prompt）来验证 voter 的降噪价值。
3. **成本观测**：单个 97 行 diff 消耗 5 个 finder 调用 + 14 个 voter 调用 = 19 次子代理运行。生产化时需要：voter 批量复核（一次调用审多条）、finder 用便宜模型、按风险分级决定是否启动全团。

## 4. 局限（诚实边界）

- 单一 PR、小 diff、合成 bug——bug 是我埋的，可能"天然好找"；需要他人盲埋语料 + 真实历史 commit 复测
- finder/voter 全部同模型，异质性只来自 persona；跨模型异质（DeepSeek 写、异模型审）的增量未测
- 未测收敛控制（本轮一轮即完成，无人机互卷场景）

## 5. 评价框架（"怎么判断评审团好不好"的正式答案）

四层指标，全部需要 baseline 对照才有意义：

1. **召回**：埋雷集上的命中率（目标 ≥ 单审 +30%，本次 +60%）
2. **精确度**：干净 diff 上的误报率（目标 ≤5%；本次双方均 0，待噪声集考验）
3. **证据质量**：file:line 可定位率（100%）+ voter 复核通过率
4. **工程指标**：收敛轮数有界（P95 ≤ 3）+ 每 PR 净 token 成本（本次 19 调用，需优化至 ≤8）
